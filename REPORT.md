# ДЗ1. Отчёт

## Результат

Сервис оценивает цену автомобиля по 12 признакам. Модель хранится в joblib вместе с
версией и порядком признаков. API сверяет входную схему с артефактом при запуске.
PostgreSQL сохраняет запросы к `/v1/predict` со статусами `200`, `422` и `500`.

## Семь вопросов

1. Время первого и второго `build` запишу из логов двух прогонов. Слой `uv sync`
   после копирования `pyproject.toml` и `uv.lock` может браться из кэша, если
   зависимости не менялись.
2. В Deployment сначала указан локальный образ `what-s-price:1.0`. CI сразу
   меняет его на образ с SHA; старые поды могут остаться с `ImagePullBackOff`,
   пока новый ReplicaSet успешно проходит rollout. Проверю это по логу deploy.
3. Пароль вводится в GitHub Actions Secret `DB_PASSWORD`, передаётся шагу
   deploy как переменная и создаёт Kubernetes Secret. Под берёт из него
   `DATABASE_URL`. ConfigMap хранится открытым текстом, поэтому пароль туда
   класть нельзя.
4. Без `needs: tests` образ может собраться из коммита с падающими тестами.
   Тогда в GHCR окажется неисправная версия сервиса.
5. На pull request запускается только `tests`: у `build` стоит условие
   `github.event_name == 'push'`, а `deploy` зависит от `build`. Публикация
   образа и развёртывание идут после push в `develop` или `main`.
6. `pg_advisory_xact_lock` сериализует создание таблицы при одновременном
   старте двух реплик API. Без него обе могут одновременно выполнять DDL
   на пустой базе; одна из них рискует не запуститься из-за конфликта.
7. Ожидаемый порядок: `Pending` при нехватке памяти до планирования на узел,
   `CreateContainerConfigError` при отсутствующем секрете до старта контейнера,
   `CrashLoopBackOff` при неверном пути к модели после повторных падений API.
   Сверю статусы с тремя красными прогонами.

### Нагрузка и HPA

Locust обращался к Ingress `price.localhost`: пять запросов `POST /v1/predict`
на один `GET /health`. Полные CSV находятся в [docs/benchmarks/sem3](docs/benchmarks/sem3).
Прогоны на 10 и 30 пользователей длились по минуте, на 60 — четыре минуты.
Они запускались последовательно, поэтому результаты не являются изолированными
сравнимыми измерениями.

| Пользователей | Реплики | CPU на pod | Запросов | RPS | Медиана, мс | p95, мс | Ошибки |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 2 (черновик) | ~55m (черновик) | 2 794 | 46,72 | 19 | 460 | 0 |
| 30 | 6 (черновик) | ~320m (черновик) | 8 218 | 138,38 | 45 | 240 | 0 |
| 60 | 6 | 600–900m | 33 867 | 141,69 | 190 | 840 | 8 (0,024%) |

Все 8 ошибок в последнем прогоне — HTTP 502 при `POST /v1/predict`; Locust
зафиксировал их между 18:20:26 и 18:23:08 UTC. Из имеющихся логов причину
502 определить не удалось. С 30 до 60 пользователей RPS почти не вырос, а
p95 поднялся с 240 до 840 мс.

Диагностический повтор на 60 пользователей дал [1 ошибку 502 из 23 546
запросов](docs/benchmarks/sem3/run60diag_stats.csv). [Журнал
Traefik](docs/benchmarks/sem3/traefik_5xx.jsonl) показывает ответ 502
для `POST` к адресу работающего pod; API не регистрировал ответ 502.
Возможная причина — повторное использование соединения, которое Uvicorn
[закрыл после 5 секунд простоя](https://www.uvicorn.org/settings/#timeouts),
тогда как Traefik [по умолчанию хранит его
дольше](https://doc.traefik.io/traefik/reference/routing-configuration/http/load-balancing/serverstransport/).
В Traefik задан `idleConnTimeout=1s`. После этого [четырёхминутный
прогон](docs/benchmarks/sem3/run60fixed_stats.csv) завершился с 0 ошибками
на 42 912 запросов по итоговому CSV; p95 составил 660 мс. Это подтверждает пользу настройки
в данном прогоне, но не доказывает причину каждого прежнего 502.

В [замерах HPA](docs/benchmarks/sem3/hpa60.csv) перед нагрузкой было 2 реплики.
При 919% CPU от `requests.cpu` HPA выставил 4, затем 6 реплик (в 18:19:58 и
18:20:13 UTC). После окончания нагрузки CPU упал до 3–11%, но 6 реплик
сохранялись в течение окна стабилизации. В 18:29:11 UTC HPA запросил 2
реплики, к 18:29:26 они остались работающими. Пик наблюдаемой памяти пода
составил 207 MiB; `requests.memory` увеличен с 256 до 288 MiB, что даёт
около 39% запаса относительно этого пика. После изменения ресурсов rollout
и smoke с записью в PostgreSQL прошли.

### Восемь вопросов

1. `tests` и `build` работают на GitHub-hosted runner: им нужны исходники, зависимости и
   доступ к GHCR. Локальный kind находится за домашней сетью и не доступен этому
   runner напрямую. Доступ можно организовать через VPN, туннель или pull-based
   GitOps, но self-hosted runner проще для проверки локального кластера.
2. `--network kind` даёт контейнеру runner доступ к именам и адресам узлов kind,
   включая `ml-pro-sem3-control-plane`. Docker socket нужен командам `docker pull`
   и `kind load docker-image`; без него runner не видит Docker daemon. `--group-add 0`
   даёт непривилегированному пользователю runner доступ к сокету с группой `root`.
3. `kubectl create secret` завершается ошибкой `AlreadyExists` при повторном деплое.
   Режим `--dry-run=client -o yaml | kubectl apply -f -` создаёт описание Secret
   локально, а `apply` создаёт его впервые и обновляет при следующем запуске.
4. `challenger` указывает на последнюю зарегистрированную кандидатную версию;
   `champion` — на ту, которую пропустил гейт по MAE. Сервис просит алиас, чтобы
   менять модель без новой сборки образа. Перенос алиаса и перезапуск подов откатывают
   только модель; `rollout undo` откатывает шаблон Deployment и код образа.
5. Если в кластере ещё нет `champion`, загрузка модели на старте завершится ошибкой,
   а поды не пройдут пробы готовности. В k9s это видно по перезапускам пода и
   сообщению об отсутствующей модели в логах; CI остановится на `rollout status`,
   а диагностический шаг покажет те же события и логи.
6. Браузер идёт на `mlflow.localhost:80`; Docker пробрасывает порт 80 в узел kind,
   Traefik по Ingress отправляет запрос в Service `mlflow:5000`, затем в под MLflow
   на порт 5000. `--allowed-hosts` принимает ожидаемые Host-заголовки, а
   `--cors-allowed-origins` разрешает запросы UI с `http://mlflow.localhost`.
   Проброс порта задаётся при создании контейнера узла kind.
7. При двух подах и CPU 919% от `requests.cpu` формула даёт
   `ceil(2 × 919 / 60) = 31` реплику, но `maxReplicas: 6` ограничивает результат.
   На практике HPA сначала выставил 4, затем 6; рост разбит на шаги политикой
   масштабирования. После завершения нагрузки HPA сохранил 6 реплик примерно
   на пять минут и затем уменьшил их до 2, что видно в CSV наблюдений.
8. В Git лежит `.csv.dvc` с MD5 и размером файла, а сами байты CSV — в
   `../dvc-storage`. Для версии N модели нужно прочитать её `data_md5` в MLflow,
   найти коммит Git с таким MD5 в `.csv.dvc`, получить этот коммит и выполнить
   `dvc pull` / `dvc checkout`, затем сверить MD5 восстановленного CSV.
